# 性能优化案例：开奖接口 N+1 查询问题

> 通过 Jaeger 链路追踪定位性能瓶颈，优化数据库查询，响应时间从 2850ms 降低到 175ms，性能提升 93.9%

---

## 一、问题发现

### 背景

在某次压测中，发现定时开奖任务执行缓慢，当参与人数超过 100 人时，单次开奖耗时达到 **2.8 秒**，导致定时任务积压，部分抽奖无法按时开奖。

### 现象

- **监控告警**：Prometheus 显示 `AnnounceLottery` RPC 接口 P99 响应时间超过 3000ms
- **用户投诉**：部分抽奖过了开奖时间仍未开奖
- **日志异常**：Asynq 定时任务队列出现大量 timeout 日志

---

根据 Jaeger Span 的 Tags，找到问题代码位置：

查看原始代码（**问题代码**）：

```go
func (l *AnnounceLotteryLogic) DrawLottery(ctx context.Context, lotteryId int64, 
    prizes []*model.Prize, participantor []int64) ([]Winner, error) {
    
    // 初始化每个用户的中奖倍率为1
    RationsMap := make(map[int64]int64)
    for _, participant := range participantor {
        RationsMap[participant] = 1
    }
    
    // ❌ 问题点：循环查询每个用户的打卡记录（N+1查询）
    for _, userId := range participantor {
        records, err := l.svcCtx.ClockTaskRecordModel.GetClockTaskRecordByLotteryIdAndUserId(
            lotteryId, userId) // 每次查询1个用户
        if err != nil {
            return nil, err
        }
        for _, record := range records {
            RationsMap[userId] += record.IncreaseMultiple
        }
    }
    
    // ... 后续抽奖逻辑
}
```

### 问题分析

- **典型的 N+1 查询问题**：有 N 个参与者，就会执行 N 次数据库查询
- 当参与人数为 127 人时，执行了 127 次 `SELECT * FROM clock_task_record WHERE lottery_id = ? AND user_id = ?`
- 每次查询耗时约 20ms，总耗时 127 × 20ms = 2540ms
- 网络往返、连接池竞争进一步增加耗时

---

## 三、优化方案

### 优化思路：批量查询

将 N 次单条查询优化为 **1 次批量查询**，使用 `IN` 子句一次性获取所有用户的打卡记录。

### 优化后代码

#### 1. 修改 Model 层，新增批量查询方法

```go
// File: app/lottery/model/clockTaskRecordModel.go

// GetClockTaskRecordByLotteryIdAndUserIds 批量查询多个用户的打卡记录
func (m *defaultClockTaskRecordModel) GetClockTaskRecordByLotteryIdAndUserIds(
    lotteryId int64, userIds []int64) ([]*ClockTaskRecord, error) {
    
    if len(userIds) == 0 {
        return []*ClockTaskRecord{}, nil
    }
    
    // 构建 IN 查询
    query := fmt.Sprintf("SELECT %s FROM %s WHERE lottery_id = ? AND user_id IN (?)",
        clockTaskRecordRows, m.table)
    
    var records []*ClockTaskRecord
    // 使用 sqlx.In 处理 IN 查询
    query, args, err := sqlx.In(query, lotteryId, userIds)
    if err != nil {
        return nil, err
    }
    
    // 重新绑定查询
    query = m.conn.Rebind(query)
    err = m.conn.QueryRowsNoCache(&records, query, args...)
    if err != nil {
        return nil, err
    }
    
    return records, nil
}
```

#### 2. 修改 Logic 层，使用批量查询


#### 3. 生成的 SQL 对比

**优化前（N 次查询）**：

```sql
-- 执行127次

SELECT * FROM clock_task_record WHERE lottery_id = 1001 AND user_id = 1002;

```

## 四、进一步优化：增加缓存

考虑到打卡记录不会频繁变更，可以增加 Redis 缓存：

```go
// 缓存 Key 设计
// lottery:clock_records:{lotteryId} -> JSON(所有打卡记录)

func (l *AnnounceLotteryLogic) DrawLottery(ctx context.Context, lotteryId int64, 
    prizes []*model.Prize, participantor []int64) ([]Winner, error) {
    
    RationsMap := make(map[int64]int64)
    for _, participant := range participantor {
        RationsMap[participant] = 1
    }
    
    // 尝试从缓存获取
    cacheKey := fmt.Sprintf("lottery:clock_records:%d", lotteryId)
    var records []*model.ClockTaskRecord
    
    err := l.svcCtx.Redis.Get(cacheKey, &records)
    if err != nil {
        // 缓存未命中，查询数据库
        records, err = l.svcCtx.ClockTaskRecordModel.GetClockTaskRecordByLotteryIdAndUserIds(
            lotteryId, participantor)
        if err != nil {
            return nil, err
        }
        
        // 写入缓存，过期时间10分钟
        l.svcCtx.Redis.Setex(cacheKey, records, 600)
    }
    
    // 统计中奖倍率
    for _, record := range records {
        RationsMap[record.UserId] += record.IncreaseMultiple
    }
    
    // ... 后续逻辑
}
```

## 六、总结与延伸

### 优化总结

1. **定位工具**：通过 Jaeger 链路追踪可视化发现 N+1 查询瓶颈
2. **优化手段**：
   - 批量查询：127 次查询 → 1 次查询
   - 增加缓存：降低数据库压力，命中率 96.5%
3. **效果显著**：响应时间从 2850ms 降低到 175ms，**提升 93.9%**

### 关键经验

- **Jaeger Span 分析**：关注占比超过 50% 的 Span，通常是优化重点
- **N+1 查询识别**：Span 树中出现大量重复的数据库查询操作
- **批量查询设计**：使用 `IN` 查询，但注意 IN 列表长度限制（建议 < 1000）
- **缓存失效策略**：用户完成打卡任务时，清除对应抽奖的缓存

### 面试回答模板

> "在性能优化方面，我通过 Jaeger 链路追踪定位到开奖接口的性能瓶颈。通过 Jaeger UI 分析 Trace，发现获取打卡记录的 RPC 调用耗时 2.6 秒，占整体耗时 94%。深入 Span 树后，发现存在 N+1 查询问题：127 个用户就执行了 127 次数据库查询。
>
> 我的优化方案是：首先在 Model 层新增批量查询方法，使用 SQL 的 IN 子句一次性获取所有用户的打卡记录，将 127 次查询优化为 1 次；其次增加 Redis 缓存，缓存抽奖的打卡记录，TTL 设置为 10 分钟，当用户完成新任务时主动清除缓存。
>
> 优化后，开奖接口的平均响应时间从 2850ms 降低到 175ms，**性能提升 93.9%**，P99 从 3.5 秒降到 210ms，缓存命中率达到 96.5%。定时任务不再积压，用户开奖准时率达到 99.8%。"
